# Spec 与 Plan 管理约定

spec 记录「为什么做、要做什么、怎样算满足需求」；plan 记录「如何实现、任务顺序、怎样验证」。这里的 plan 是工程实施计划，与产品中的家庭阅读计划不同。

## 目录与命名

```text
specs/
├── README.md
├── templates/
│   ├── spec.md
│   └── plan.md
└── 001-spec-plan-workflow/
    ├── spec.md
    └── plan.md
```

每项独立需求使用递增的三位编号和英文短名，例如 `002-reading-feedback`。编号唯一且不复用；同一需求的澄清、修正和实施阶段沿用原目录。不同需求另建目录并链接依赖。每个目录只维护一份当前 spec 和一份配套 plan。

## Spec 内容

1. **元信息**：需求 ID、标题、状态、版本、创建/更新时间、plan 相对链接和来源。版本从 `v0.1` 开始；需求、范围或验收变化递增次版本，纯排版修改不递增。
2. **最初需求**：保存首次需求原文、提出日期和来源。原文不可被后续结论覆盖；历史来源只能链接或引用，无法找回的原话注明缺失，不补造。
3. **目标与范围**：用户、问题、预期结果、包含内容、非目标及依赖。
4. **需求与验收**：用稳定的 `REQ-001` 编号记录行为与约束；用 `AC-001` 编号描述可观察的通过条件，并关联需求。
5. **待确认与变更记录**：区分用户明确要求、用户后续决定、Agent 建议/假设。逐次追加日期、讨论内容、决定来源和受影响编号；旧需求撤销时保留编号并标注替代项。

长讨论可以保存必要原文摘录和准确摘要；不得把 Agent 方案写成用户已确认的决定。业务 API、数据规则、错误行为等只在相关需求中补充。

## Plan 内容与对应关系

- 元信息链接 spec，并记录实施所依据的 spec 版本。
- 记录实施方案、影响路径、任务顺序、依赖和必要的迁移措施。
- 每项任务使用 `TASK-001` 编号，并列出关联 `REQ-*`、`AC-*` 及验证方式。
- 用对应表覆盖全部当前有效需求，包含任务、验收项、验证证据与结果。一个需求可以对应多个任务，一个任务也可以覆盖多个需求。
- 暂不实施的需求记录延期原因与后续安排；验证失败、未执行和通过分别记录。完成状态需要实际证据，不能仅凭任务勾选或代码已存在。

## 每次讨论后的维护步骤

1. 查索引定位已有需求；新需求复制两个模板并替换占位符，更新索引。
2. 保留初始原文，追加本轮讨论记录，更新当前需求、验收、待确认项和版本。
3. 同步 plan 的基线版本、任务和对应表。纯讨论也维护 plan，任务可以待开始；影响实现的未知项标为依赖，继续处理不受影响的部分。
4. 实施中按需求编号推进；发现需求变化先更新 spec 和 plan，再执行受影响的任务。不要根据已有代码反向改写原始目标。
5. 收尾补充真实验证结果、剩余事项和状态，同步索引，并在回复或 PR 中链接该需求的 spec/plan。

状态采用 `draft`、`ready`、`in-progress`、`implemented`、`archived`；`ready` 表示范围足以实施，未解决的问题不影响当前任务。`implemented` 必须满足本次范围内全部验收；取消或被替代的需求归档并注明原因。索引状态与两个文档保持一致。
