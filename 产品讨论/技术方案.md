# 儿童英语阅读辅助产品技术方案

> 状态：技术方案 v0.1，更新于 2026-09-23。本文是设计契约，不包含实现代码。产品范围以 [product.md](product.md) 和用户最新决定为准。

## 0. 决策状态与建设阶段

### 已确定

- 采用前后端分离；公开业务接口统一以 **`/baby/study`** 为路径前缀。
- 第一阶段先让系统可运行、可录入和查看真实数据；后续接入 Agent 与本体推理，形成评估、建议、反馈、状态更新和计划调整的核心循环。
- 产品服务 1.5～7 岁孩子；第一版仅管理一个孩子。家长拥有最终选书权；原始回答和反馈必须保留。

### 本方案的技术建议

- 一个代码仓库中分别管理前端和后端；前端、后端分别构建，通过 HTTP API 通信。
- V0 采用 React、TypeScript、Vite、Django、Django REST Framework 和 PostgreSQL。框架与托管商属于建议，并非产品需求。
- V0 的计划可由家长手动确认并使用少量明确规则。V0 是可运行的技术底座；[product.md](product.md) 中“有依据的持续调整”等完整产品验收，需要后续推理循环才能达到。
- Agent 和本体推理先保留清晰的输入、输出及权限边界；不在 V0 部署空转的推理服务、队列或图数据库。

| 阶段 | 要完成的能力 | 完成定义 |
|---|---|---|
| V0：可运行系统 | 登录、一个孩子、图书与书架、问卷回答、家长确认的短周期计划、共读与反馈、历史查询 | 可以在手机上完成一轮“看今天的任务—共读—提交反馈”，数据可再次查看 |
| V1：核心逻辑循环 | Agent 提取文字中的候选观察；本体概念和推理规则结合证据提出状态与内容建议；调整未执行的计划 | 建议带依据，关键判断可由家长确认或纠正，计划变化可追溯 |
| 后续扩展 | 更丰富的图书元数据、多孩子、更多分级体系与更复杂的推理 | 由真实使用需求决定 |

## 1. 推荐技术栈与比较

| 层次 | 推荐 | 理由 |
|---|---|---|
| 前端 | React + TypeScript + Vite | 独立开发响应式页面，构建产物为静态文件，适合独立前后端和个人维护 |
| 后端 | Python + Django + Django REST Framework | 提供 JSON API，同时利用 Django 的迁移、账户和图书管理后台 |
| 数据库 | PostgreSQL | 适合图书、来源、问卷、证据和计划版本之间的关系及事务写入 |
| 页面与接口 | 手机和平板优先的 Web 页面；同域名下通过 `/baby/study` 访问 API | 先满足家庭试用，避免 V0 同时维护移动端安装包 |
| V1 的文字解析 | 一个服务端模型适配接口，供应商由实际部署地域确定 | 解析结果只作为待确认的观察候选，不直接写孩子状态或计划 |

相比之下，Next.js 加独立 Python 后端会让当前项目多维护一套服务端页面能力；纯前端加 FastAPI 虽然也合理，但首批图书资料需要人工核对，Django 管理后台有直接价值。上述比较以本项目的个人开发和资料维护需求为依据，不代表其他方案不可用。

相关官方资料：[Vite React/TypeScript 模板](https://vite.dev/guide/)、[Django 5.2 长期支持说明](https://docs.djangoproject.com/en/5.2/releases/5.2/)、[Django REST Framework 快速入门](https://www.django-rest-framework.org/tutorial/quickstart/)。具体小版本在启动开发时锁定并核对兼容性。

## 3. 核心模块和职责

| 模块 | V0 职责 | V1 增量 |
|---|---|---|
| 前端应用 | 建档、书架、问卷、今日任务、反馈和历史页面；呈现后端给出的解释 | 呈现证据、候选观察、追问和计划调整建议 |
| 图书目录与书架 | 系统书目与家庭书架均逐本登记；系列按套装/级别/版本分组，支持整组加入与折叠展示，状态仍逐本记录 | 为推理提供内容特征和来源可信度 |
| 评估与证据 | 保存家长原始回答及可直接确认的事实 | 从反馈中产生候选观察，保存确认、纠正及证据关系 |
| 计划与执行 | 家长建立或调整短周期计划，保存任务和实际完成情况 | 根据状态和规则提出有依据的推荐与计划新版本 |
| Agent 接口 | V0 不调用模型；保留反馈原文和必要的字段 | 解析文字、发现歧义并提出追问；无直接数据库写权限 |
| 本体与推理 | 定义孩子、活动、资源、观察和计划的术语及关系；不运行通用推理引擎 | 读取事实与规则，产出带依据的状态及推荐提案 |

本体推理与 Agent 分工：**本体及规则解释事实之间的关系，Agent 处理自然语言输入和表达；后端业务服务校验并应用家长确认的结果。**“能生成符合结构的数据”不等于“教育判断正确”。

## 4. 核心数据模型

| 实体 | 第一阶段需要保留的信息 | 后续用途 |
|---|---|---|
| `User`、`Learner` | 家长账户、一个孩子的出生年月及家庭约束 | 适龄约束和个人状态；年龄不等于能力 |
| `Book` | 实际读物及版本，书目、封面、主题、阅读属性 JSON、身份标识；历史主系列/说明/来源保留 | 版本级资料与单本状态 |
| `BookSeries` | 具体套装/级别/版本，品牌、别名、套装 ISBN、封面、内容、预期册数与完整性 | 搜索与加入已收录分册 |
| `SeriesMembership` | 单本与套装多对多、顺序、唯一成员约束；共享单本复用ID | 各组展示共享状态，总数去重 |
| `CatalogImportRecord` | 原文件、工作表、行号、原文、候选及缺失/失败原因；私有购买信息不公开 | 导入核对与历史映射 |
| `SourceEvidence` | 具名单本/套装字段声明、公开URL、时间、核验状态；后台修改字段自动锁定 | 资料可追溯、人工优先 |
| `BookLevelClaim` | 原生分级或蓝思声明、书的版本、来源、核验状态 | 推理时区分可靠数据与参考映射 |
| `ShelfItem` | 用户与单本图书的唯一关系、拥有状态、阅读状态 | 限定实际可执行的任务 |
| `Assessment`、`AssessmentAnswer` | 问卷版本、原始答案和“不确定”回答 | 重新解释初始状态，不覆盖历史答案 |
| `Plan`、`PlanRevision`、`Task` | 周期、版本号、任务日期、读物、建议活动与家长决定 | 调整只影响尚未执行的任务 |
| `ReadingSession`、`ParentFeedback` | 是否进行、时长、参与情况、家长原文与时间 | 形成新的观察证据；未读不等于能力下降 |
| `Observation`、`LearnerStateVersion` | 观察来源、确认状态、发生时间；状态结论与依据 | V1 逐步启用的证据和推理结果 |

图书允许缺失蓝思值。现有清单的 66 条记录蓝思值均为空；两张分级图片只能作为对照参考，不能成为单本书经核验的数值。初始迁移保留19条来源；003已覆盖全部66行检索，逐项可靠先入库，待确认项详见 [核对报告](../imports/catalog-review.md)。书名相似只生成候选，ISBN区分套装/单本，同版本合并需明确来源映射。采集脚本缓存、限速、重试、续跑；导入逐行事务、dry-run/apply；CI只使用固定样本。

## 5. `/baby/study` 接口契约

### 固定规则

1. **`/baby/study` 是公开业务 API 的固定根路径**。本方案不再使用先前建议的 `/api/v1`。前端页面可以部署在同域名的其他路径，不能占用此 API 根路径。
2. API 使用 JSON；字段名统一为 `snake_case`。时间返回包含时区的 ISO 8601 值；服务端统一保存绝对时间，按家庭时区展示日期和“今天”。
3. 读取使用 `GET`，创建使用 `POST`，更新资源使用 `PUT` 或 `PATCH`。成功时返回业务资源及其 `id`；错误至少返回 `error.code`、`error.message`，校验错误附 `error.details`。
4. 所有业务接口要求登录。浏览器使用同域会话；修改请求校验 CSRF。V0 不开放公共注册。DRF 对会话认证下的写请求有 CSRF 要求：[官方说明](https://www.django-rest-framework.org/api-guide/authentication/)。
5. 保存反馈等可能重试的创建请求使用 `Idempotency-Key`；修改计划时提交所依据的 `revision`。版本冲突返回冲突信息，不静默覆盖。
6. 根路径和已发布字段语义保持稳定。后续优先做兼容性新增；确需破坏性变更时，先明确迁移和版本方案，不直接改变旧契约。

### V0 业务接口

| 方法与路径 | 最小输入 | 主要输出与语义 |
|---|---|---|
| `GET/PUT /baby/study/learner` | 出生年月、目标、时间约束 | 当前孩子档案；出生年月用于适龄判断 |
| `GET /baby/study/books` | 可选 `q`（书名或系列）和 `language` | 保留 `books` 单本结果，新增 `series`（完整成员、总册数、当前用户已拥有册数）；单本增加 `series_ids`、系列摘要、封面及基础资料；可空 `series_id`、`series_name` 保持兼容；蓝思值缺失返回 `null` 和 `missing` |
| `GET /baby/study/books/{id}`、`GET /baby/study/series/{id}` | ID | 完整书目、版本、阅读属性、成员及字段来源；不返回私有原表 |
| `GET /baby/study/shelf` | 无 | 当前用户已确认拥有的家庭书架 |
| `PUT /baby/study/shelf/{book_id}` | `ownership_status`、`reading_status` | 幂等设置单本状态；加入为 `owned/unread`，移出为 `not_owned/null` |
| `POST /baby/study/shelf/series/{series_id}` | 无业务字段，可发送 `{}` | 服务端取已收录实际成员，事务内加入缺少的分册为 `owned/unread`，保留已拥有状态及时间；返回 `added_count`、`already_owned_count`、`total_count` |
| `GET /baby/study/assessment/questions` | 无 | 问卷版本和当前可回答的问题 |
| `POST /baby/study/assessments` | `questionnaire_version`、逐题答案 | 评估记录 ID；保留原始回答，不强制输出能力等级 |
| `GET /baby/study/plans/current` | 无 | 当前计划、`revision` 与各任务 |
| `POST /baby/study/plans` | 周期及家长确认的任务 | 新计划 ID、初始 `revision` |
| `PATCH /baby/study/plans/{plan_id}/tasks/{task_id}` | 任务变更、预期 `revision` | 新计划版本；已完成任务不可被改写 |
| `GET /baby/study/today` | 无 | 今天的任务和可解释的已知信息 |
| `POST /baby/study/tasks/{task_id}/feedback` | `completion`、可选时长、参与情况、行为标签和原文 | 反馈 ID；无模型时也能立即保存 |
| `GET /baby/study/history` | 可选日期范围 | 已发生的共读及原始反馈 |

最低限度的状态枚举应在落地时写入接口规范：`ownership_status` 区分已确认拥有、未拥有和未知；`reading_status` 区分未读、近期在读、熟悉和暂停；`completion` 区分完成、部分进行和未进行。未知与缺失值不能被转换成负面能力结论。

书目添加与编辑使用 Django 管理后台，不开放业务写入接口。首位家长通过管理员账户登录，前端与管理后台共享会话；本地前端开发服务器代理 `/admin` 和 `/static`。

2026-09-29 设计更新：[004 Spec](../specs/004-catalog-management-ai/spec.md) 已确认管理员通过前台新增和归档共享书目，开放受会话/权限/CSRF 保护的业务写入 API；归档保留书架及历史引用，不直接物理删除。混合照片逐图提取并自动分组，疑点可纠正，统一确认后事务入库，可选联网补全。通用编辑/误删恢复另作候选。本段是新设计范围，现有业务 API 仍只读书目，实施与验证见 [004 Plan](../specs/004-catalog-management-ai/plan.md)。

### V1 扩展接口与后端内部契约

未来在同一根路径增加状态、推荐、待确认观察和家长决策接口，例如 `/baby/study/state`、`/baby/study/recommendations`、`/baby/study/observations/pending`。这些路径目前只固定**归属范围**，请求字段与具体行为需在评估及推理规则确定后另行定稿，不能当作 V0 已开放接口。

后端内部先保持两项清楚的契约：

- `提出学习建议`：读取已确认的状态、证据、书架和家庭约束，返回候选内容、理由、证据缺口与需家长确认的变更。
- `提取反馈观察`：读取家长反馈原文，返回候选行为、对应原文片段、不确定之处和建议追问；不能直接写状态或改计划。

未来的 Agent 与推理器只能通过这些受控业务接口工作。原始答案、原始反馈、已完成任务和历史计划版本不可被其覆盖。

## 6. 外部服务和环境变量

V0 只依赖 PostgreSQL。建议环境变量：`DATABASE_URL`、`DJANGO_SECRET_KEY`、`DEBUG`、`ALLOWED_HOSTS`、`CSRF_TRUSTED_ORIGINS`、`APP_TIME_ZONE`；前端仅配置公开的 `API_BASE_PATH=/baby/study`，不得包含密钥。

V1 接入模型时，再增加服务端的 `MODEL_API_KEY`、`MODEL_BASE_URL`、`MODEL_NAME` 和调用超时。阿里云百炼可作为中国大陆部署情境下的候选服务，其官方文档列出北京地域接入和部分模型的 JSON Schema 输出；具体可用模型与地域在实施时核验：[地域说明](https://help.aliyun.com/zh/model-studio/regions/)、[结构化输出说明](https://help.aliyun.com/zh/model-studio/qwen-structured-output)。OpenAI API 不作为默认依赖；其官方支持地区列表目前未列出中国大陆：[OpenAI API 支持地区](https://developers.openai.com/api/docs/supported-countries)。

2026-09-29 供应商与阶段更新：上述为早期候选方案，用户现已指定 MiMo，采用 OpenAI 兼容协议。本期实际接通验证文字生成、图片理解、音频理解，家长 Agent 页面后续做。服务端分别配置实时和 Batch 地址及模型；图书识别全部默认 Batch，用户可切换实时，不自动提高调用成本。Key 仅放在未跟踪的服务端配置。官方能力及文档差异见 [004 Spec](../specs/004-catalog-management-ai/spec.md)，尚无真实 API 联调结果。

## 7. 本地开发方式

本地分别运行前端开发服务器和 Django API，PostgreSQL 通过 Docker Compose 启动。前端开发服务器将 `/baby/study` 请求转发至后端；正式环境仍保持同一路径。先导入图书候选，再由家长确认实际拥有与可用状态。V0 的开发和测试均不要求模型密钥。

## 8. 测试策略

- **API 契约测试**：固定根路径、字段、登录与 CSRF、错误结构、重复提交及计划版本冲突。
- **数据导入测试**：19 条单本来源可追溯；空蓝思值保持为空；待核对的套装和级别不会被当作单本导入。
- **业务规则测试**：年龄不能单独决定能力；未进行不产生能力下降证据；家长指定读物保留最终选择权；已完成任务不被重排。
- **端到端测试**：在手机尺寸完成确认书架、问卷、查看今天、提交反馈和回看历史。
- **V1 增补**：用匿名化反馈样例检查文字提取、追问和家长确认；验证推理结果有依据且无法绕过业务写入规则。
- **部署检查**：正式保存真实家庭数据后定期验证数据库备份可以恢复。

## 9. 部署方式

先在本地完成 V0 试用。需要持续远程访问时，可在一台可稳定访问的小型服务器上分别运行前端静态资源、Django API 和 PostgreSQL，通过反向代理把 `/baby/study` 指向 API，其余前端页面指向静态资源，并启用 HTTPS。数据库备份存放在服务器之外。部署地域目前未确认，应根据实际使用地点与模型服务可用地域选择；不把某一家托管商写入业务契约。

## 10. 未来扩展点

后续可以逐步增加 Agent 反馈解析、本体规则推理、资料来源审核、跨分级体系参考、更多孩子与照护者、提醒、语音或图片反馈。只有在推理规模或运行时间确实需要时，才考虑独立后台任务服务；只有在关系推理需求超出关系数据库与明确规则能力时，才评估 RDF/OWL、图数据库或专用推理引擎。

## 11. 主要技术风险

1. **前后端契约漂移**：接口根路径与基础字段固定后，双方必须按同一契约测试；未来变更先做兼容性设计。
2. **基础系统与产品价值之间存在阶段差**：V0 可以运行和记录数据，但还不能声称已实现个性化学习循环；需要以 V1 的证据驱动建议验证产品目标。
3. **图书数据不足**：缺失的蓝思值、套装版本和来源会降低建议可靠度；显示不确定性并保留人工核对入口。
4. **模型输出看似合理却解释错误**：结构化格式不能替代事实核验，重要观察和明显调整需要家长确认。
5. **儿童数据与服务可用性**：仅收集必要数据，模型调用时减少个人信息，服务不可用时仍能记录反馈。
6. **过早引入推理基础设施**：先用可追溯的事实和明确规则验证循环，再选择是否需要专用本体技术。

2026-09-28 003 后续变更：成员表是统一维护入口，保留旧主系列字段作兼容；`total_count` 为实际成员数，`expected_count` 未知为null，完整性明确。全体写入沿用用户行锁，批量加入一次性、不自动订阅新分册。详见 [图书接口文档](catalog-api.md)。
